# Factor DSL Safety and Correctness Design

## Goal

Strengthen the Factor DSL boundary so every formula entering factor execution is structurally safe, free from negative or zero lookback windows, and consistent with its declared `FactorSpec` metadata, while preserving the behavior of currently valid formulas.

## Scope

This phase covers:

- strict validation of formula ASTs, fields, operators, and window arguments;
- rejection of negative, zero, non-integer, and oversized lookback windows;
- detection of the fields and maximum window referenced by a formula;
- consistency checks for `required_fields` and `lookback`;
- replacing direct `eval` execution with a controlled AST interpreter;
- regression and security tests for the validator and executor.

This phase does not add a factor registry, multi-factor portfolio construction, transaction-cost modeling, historical index membership, or a separate-process sandbox. Those belong to later phases.

## Current Risk

The current validator checks AST node and name allowlists, but it does not validate call arguments. A formula such as `delay(close, -1)` can therefore reach the operator layer and request forward data. The executor then evaluates the validated expression with `eval`; its empty `__builtins__` environment reduces risk but is not a complete semantic execution boundary. `FactorSpec.required_fields` and `lookback` are also declarations rather than values derived from the formula.

## Design

### Formula Validation

`FactorDslValidator` remains the public validation entry point and returns `FactorDslValidationResult`. It will parse the formula once and inspect the resulting AST recursively.

The validator will:

1. reject unsafe tokens and unsupported AST node types;
2. allow only whitelisted fields and operators;
3. require every operator argument to match the operator's declared signature;
4. require rolling and delay windows to be integer constants in the range `1..MAX_WINDOW`;
5. reject negative, zero, non-integer, and oversized windows;
6. reject formulas exceeding a bounded AST node count, call depth, or source length;
7. derive the formula's referenced fields and maximum window;
8. require `required_fields` to equal the derived field set;
9. require `lookback` to be at least the derived maximum window;
10. return stable, machine-readable error codes for each failure.

The operator signature table will be explicit. For example:

```text
returns(x, window)      -> windowed, positive integer window
delay(x, window)        -> windowed, positive integer window
ts_mean(x, window)      -> windowed, positive integer window
ts_std(x, window)       -> windowed, positive integer window
ts_min(x, window)       -> windowed, positive integer window
ts_max(x, window)       -> windowed, positive integer window
rank(x)                 -> unary
zscore(x)               -> unary
winsorize(x, lower, upper) -> bounded numeric optional arguments
neutralize(x, by)       -> binary series arguments
```

The first implementation will preserve the existing formula surface. It will not introduce new operators or silently rewrite invalid formulas.

### Controlled Execution

`FactorExecutor` will validate the `FactorSpec`, parse the formula, and evaluate only the supported AST node types through a small recursive interpreter. The interpreter will resolve:

- field names from the validated data-column environment;
- operator names from the validated operator registry;
- numeric constants;
- arithmetic operations already allowed by the validator;
- unary negation already allowed by the validator.

It will not call Python `eval`, expose builtins, allow attributes/subscripts, or permit dynamic function lookup. The result must remain a Pandas `Series` with the expected market-data index.

### Metadata Consistency

The validator will derive formula metadata from the AST rather than trusting declarations. A formula that references `close` and uses a 60-day rolling window must declare `required_fields=["close"]` and `lookback >= 60`. The error should identify both the declared and derived values.

### Compatibility

Existing valid formulas generated by `FactorDslGenerationService` must continue to validate and execute with the same numerical results. Formula metadata that was previously under-declared will be rejected and must be corrected in the generator or fixture data rather than silently accepted.

## Error Handling

Validation errors remain non-fatal at the workflow level when other factor specs are valid. `ValidateDSLNode` will exclude invalid specs and append a warning containing the factor name and stable error codes. If no valid spec remains, the existing deterministic fallback behavior remains in place, but the fallback must itself pass the stricter validator.

Execution errors remain isolated per factor. A formula that raises because of data shape or numeric issues is recorded as a factor execution warning; the workflow fails only when no factor can execute.

## Testing Strategy

Add focused tests for:

- valid nested formulas and all current operators;
- negative, zero, non-integer, and oversized windows;
- unknown fields and operators;
- attributes, subscripts, comprehensions, lambdas, and other unsupported AST nodes;
- formula source length and AST complexity limits;
- derived-field and `lookback` metadata mismatches;
- deterministic execution results for existing valid formulas;
- rejection of formulas that would request forward data;
- executor behavior when the result is not a Pandas `Series`;
- workflow fallback when all supplied specs are invalid.

The existing factor, graph, and API tests must continue to pass. Numerical regression tests will use small deterministic MultiIndex fixtures and compare Series values with a floating-point tolerance.

## Acceptance Criteria

The phase is complete when:

1. no negative or zero time window can pass validation;
2. no formula can access a field or operator outside the registry;
3. formula metadata mismatches are rejected with actionable error codes;
4. factor execution no longer relies on direct `eval`;
5. all existing valid demo formulas produce unchanged results;
6. new security and regression tests pass together with the full test suite;
7. the research report continues to expose validation warnings and fallback diagnostics.

## Follow-up Boundaries

The next phase will use this validated DSL boundary to add realistic execution assumptions, transaction costs, historical universes, and stronger out-of-sample evaluation. The later factor-library phase will persist validated specs and their research lineage as versioned catalog entries.
